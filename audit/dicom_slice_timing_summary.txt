=== DICOM FIELDS FOUND (relevant to slice timing) ===

AcquisitionTime (0008,0032): present, but IDENTICAL across all slices within a given volume
  (confirmed by direct inspection of multiple slices sharing one TemporalPositionIdentifier,
  across two independently-sampled series from different scanner-software versions).
TriggerTime (0018,1060): present, also constant per volume; empirically equals
  a fixed linear function of (TemporalPositionIdentifier x true volume TR) plus a constant
  offset -- i.e. it encodes the volume's start time, not any per-slice offset.
TemporalPositionIdentifier (0020,0100): present; identifies the VOLUME index (1..N), not slice.
(2001,100A) [Slice Number MR] (Philips private): present; a per-slice SPATIAL index (1..num_slices).
  This is genuine per-slice metadata NOT present anywhere in the BIDS JSON sidecars. However,
  no field in the DICOM header (standard or private) explicitly states the TEMPORAL acquisition
  order/scheme (sequential ascending/descending/interleaved) for these slices. Spatial index
  cannot be safely assumed to equal temporal acquisition order without that explicit statement,
  particularly for EPI sequences which commonly use interleaved acquisition.
SliceLocation (0020,1041) / ImagePositionPatient (0020,0032): present; spatial position only.
No Enhanced MR multi-frame per-frame functional groups were present (these are classic
single-frame DICOM files, one instance per slice-per-volume).

=== DICOM -> BIDS COMPARISON ===

Slice timing/order: SliceNumberMR and SliceLocation exist in DICOM but are NOT carried into the
BIDS JSON sidecars at all (0/175 sidecars contain any per-slice field). This is a genuine loss of
per-slice spatial metadata during DICOM->BIDS conversion -- however, since this metadata only ever
encoded spatial index (not confirmed temporal order), its loss does not change the conclusion that
exact slice timing was never recoverable, with or without BIDS conversion.

TR: 22 of 170 matched series show the DICOM header's (0018,0080)
RepetitionTime as roughly HALF the true effective volume-to-volume interval. The true interval was
independently confirmed two ways for affected series: (a) AcquisitionDuration / NumberOfTemporalPositions,
and (b) direct empirical AcquisitionTime deltas between consecutive volumes (same slice, different
TemporalPositionIdentifier) -- both align with the larger value, and with BIDS's own RepetitionTime.
This means BIDS's RepetitionTime is the MORE reliable field for these runs; the raw DICOM (0018,0080)
tag under-reports the true TR by roughly 2x for the affected acquisitions. No information was lost in
this respect -- BIDS actually corrected/reflected the true timing better than the raw per-instance tag.

Examples:
  sub-019S5019 ses-01: DICOM header TR=2999.99853515625ms, empirical TR=3063.93ms, BIDS TR=3s
  sub-019S5012 ses-01: DICOM header TR=2999.99853515625ms, empirical TR=3063.93ms, BIDS TR=3s
  sub-002S0413 ses-01: DICOM header TR=3000.0ms, empirical TR=6042.86ms, BIDS TR=6.02158s
  sub-002S0685 ses-01: DICOM header TR=3000.0ms, empirical TR=6042.86ms, BIDS TR=6.02158s
  sub-002S2010 ses-01: DICOM header TR=2250.0ms, empirical TR=2298.21ms, BIDS TR=2.25s
  sub-002S2043 ses-01: DICOM header TR=3000.0ms, empirical TR=6042.86ms, BIDS TR=6.02158s
  sub-002S4171 ses-01: DICOM header TR=3000.0ms, empirical TR=6042.86ms, BIDS TR=6.02158s
  sub-002S0729 ses-01: DICOM header TR=3000.0ms, empirical TR=6042.86ms, BIDS TR=6.02158s

Number of slices / number of volumes: NumberOfSlicesMR and NumberOfTemporalPositions (DICOM) agree
with the Z dimension and volume count seen in the converted NIfTI for all EXACT_VOLUME_SLICE_MATCH
pairs (that agreement is, in fact, the basis used for matching them in this audit).

Known problematic run (sub-012S4026_ses-01, 7 volumes in BIDS): checked directly against raw_data.
Confirmed the ENTIRE raw DICOM archive contains exactly 1 .dcm file for this subject/session
(ADNI/012_S_4026/Resting_State_fMRI/2011-12-07_10_02_11.0/I274420), not the ~6720 expected for a
full 140-volume x 48-slice acquisition. This is not a BIDS-conversion or matching artifact -- the
source DICOM data was already incomplete before conversion. Nothing was deleted or altered to
confirm this; it was a direct read of the archive's existing contents.

=== FINAL CONCLUSION ===

3. SLICE_TIMING_NOT_RECOVERABLE

Evidence:
- AcquisitionTime and TriggerTime, the only per-instance DICOM timestamp fields present, were
  directly and repeatedly confirmed IDENTICAL across every slice within a given volume, in two
  independently sampled series from different sites/scanner-software versions. There is no field
  anywhere in the DICOM data (standard tags or Philips private groups 2001/2005) that records a
  distinct acquisition instant for individual slices within a volume.
- (2001,100A) Slice Number MR provides a genuine per-slice SPATIAL index, but no field explicitly
  states the temporal acquisition order/scheme (e.g. sequential vs. interleaved), so this index
  cannot be safely equated with acquisition order without an unverified assumption -- which this
  audit was explicitly instructed not to make.
- Therefore neither exact slice timing (category A/C) nor a confirmed slice acquisition order
  (category B) can be established from the available DICOM metadata. This is a definitive,
  evidence-based negative finding, not a case of insufficient data (category D) -- the data was
  extensive and specific; it simply does not contain the needed information.
- No SliceTiming values were inferred, derived, or fabricated anywhere in this audit.
