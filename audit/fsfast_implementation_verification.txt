2. Motion correction
Status: CONDITIONAL -- data-wise supportable; NOT YET VERIFIED against the installed
  binary because no FS-FAST binary exists yet (see COMMAND AVAILABILITY above).
Implementation: mc-afni2 is the FS-FAST-native tool for this (per prior audits and public
  FS-FAST documentation), invoked directly rather than through the full preproc-sess driver
  (preproc-sess additionally assumes a FreeSurfer subject/session directory structure and
  a completed recon-all for its later steps, neither of which applies here). This
  characterization is FROM DOCUMENTATION/PRIOR AUDIT, NOT verified against the installed
  version, per the instruction not to assume behavior from a different FreeSurfer version --
  it must be re-confirmed once the binary exists (via mc-afni2 --help or equivalent).
  An alternative already confirmed via Nipype introspection: RobustRegister
  (mri_robust_register) takes only source_file/target_file, no FreeSurfer-subject or T1w
  dependency -- but it registers one 3D volume to another 3D volume, not a 4D series
  natively, so using it for full-run motion correction would require splitting the run
  into individual 3D frames and looping the registration per frame, then reassembling --
  materially different from mc-afni2's single-call 4D-in/4D-out design. This is reported
  as an available fallback option only; it is not being substituted for mc-afni2 without
  your decision.
Nipype: mc-afni2 needs a custom CommandLine node (no wrapper exists). RobustRegister has
  an EXISTING nipype interface if that path is ever chosen instead.
4D support: mc-afni2 -- expected to accept/produce 4D directly, per documentation, NOT
  verified on this installation yet. RobustRegister -- confirmed 3D-to-3D only (verified
  from its actual input spec).
T1w requirement: mc-afni2 -- none (operates in native functional space). RobustRegister --
  none (mandatory inputs are just source_file/target_file, confirmed from its input spec).

5. Temporal filtering / detrending
Status: CONDITIONAL -- mri_glmfit is confirmed (from its actual input spec, not assumption)
  to be a general-purpose GLM estimator, NOT a dedicated high-pass/low-pass filter. It has
  no --highpass/--lowpass-style flag. Detrending/filtering is achievable only by supplying
  an explicit design matrix (--X / `design` input) containing polynomial or cosine-basis
  regressors that WE must construct -- mri_glmfit does not generate them itself. This is a
  standard, legitimate regression-based filtering technique (the same principle FSL's own
  highpass filter uses internally), but it is not a single-flag operation, and must be
  built explicitly, not assumed to exist as a convenience feature.
Implementation: nipype.interfaces.freesurfer.GLMFit, in_file=4D BOLD (confirmed GLMFit's
  mandatory input accepts a 4D file directly), design=<constructed regressor matrix>.
Nipype: GLMFit -- EXISTING interface, confirmed usable, no custom node required for the
  mri_glmfit call itself. A separate (non-FS-FAST) step to construct the polynomial/cosine
  design-matrix file is needed -- this is orchestration/data-prep, not a preprocessing
  framework substitution.
